# Implementation Plan: Browser Extensions (Chrome & Firefox)

**Branch**: `006-browser-extensions` | **Date**: 2026-09-17 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/006-browser-extensions/spec.md`

## Summary

Declaratively force-install and enable four browser-extension families — a content
blocker, Bitwarden, Dark Reader, and Vimium-style keyboard navigation — in both Chrome
and Firefox for `dmiller` on the `laptop` host, using each browser's native
enterprise-policy mechanism (no manual web-store visits). Chrome uses `uBlock Origin
Lite` and `Vimium`; Firefox uses the full `uBlock Origin` and the community port
`Vimium-FF`, because the "original" extension for each isn't installable on the other
browser (see spec.md Assumptions).

## Technical Context

**Language/Version**: Nix (NixOS module system), `nixpkgs` `nixos-unstable` channel (as
already pinned in `flake.lock`)

**Primary Dependencies**: NixOS's built-in `programs.chromium` and `programs.firefox`
policy options (both ship in `nixpkgs`, no new package or flake input needed); the
extensions themselves are fetched by each browser at runtime from its own store (Chrome
Web Store / addons.mozilla.org), not packaged through Nix.

**Storage**: N/A — no repository-managed data store. Two static policy files
(`/etc/opt/chrome/policies/managed/default.json`,
`/etc/firefox/policies/policies.json`) are generated by the Nix build; each extension's
own runtime state (settings, Bitwarden login) lives in the browser's profile directory
under `dmiller`'s `$HOME`, untouched by this feature.

**Testing**: `nix flake check` and `nixos-rebuild dry-build --flake .#laptop` (per
Constitution Principle IV), followed by manual verification of each extension in each
browser per `quickstart.md`.

**Target Platform**: NixOS `laptop` host (`x86_64-linux`); Google Chrome (from
`specs/005-chrome-obsidian-bitwarden`) and Firefox (`modules/nixos/users.nix`).

**Project Type**: Single NixOS flake configuration (system modules) — not a standalone
application.

**Performance Goals**: N/A — declarative policy configuration; no custom performance
target.

**Constraints**: Must be fully declarative with no imperative install step (Constitution
Principle I); must not require browser-account sign-in (spec FR-005); must not degrade
Chrome, Firefox, or the apps from `specs/005-chrome-obsidian-bitwarden` (spec FR-006);
Chrome cannot run the full (Manifest V2) uBlock Origin under any mechanism as of 2026
(see `research.md`) — this is an external platform constraint, not a choice made here.

**Scale/Scope**: Four extension families, two browsers, one host (`laptop`), one user
(`dmiller`) — eight concrete extension installs total (four per browser).

## Constitution Check

*GATE: Must pass before Phase 0 research. Re-check after Phase 1 design.*

- **I. Declarative Configuration Only** — PASS. All eight extension installs are
  expressed as NixOS policy options (`programs.chromium.extensions`,
  `programs.firefox.policies.ExtensionSettings`); nothing is installed by visiting a web
  store by hand.
- **II. Reproducibility & Pinned Inputs** — PASS. No new flake inputs are introduced.
  The generated policy files (extension IDs and update URLs) are fully determined by
  this repo's Nix source, so `nix build` is deterministic; the *browsers* separately
  fetch the actual extension code from their own stores at runtime — the same class of
  runtime network dependency every browser already has (e.g., loading any web page), not
  a build-time impurity.
- **III. Host Modularity & Composability** — PASS. A new, dedicated module
  (`modules/nixos/browser-extensions.nix`) holds both browsers' policy config, mirroring
  the one-file-per-concern pattern already used for
  `modules/nixos/desktop-apps.nix`/`dev-tools.nix`, so a future second host can opt in
  independently.
- **IV. Build & Validate Before Merge** — PASS (planned). `nix flake check` and a dry
  build for `laptop` are required validation steps before this feature is done (see
  `quickstart.md`).
- **V. Simplicity & Incremental Change** — PASS. Both browsers use their own native,
  already-built-in NixOS policy option — no new abstraction, no new flake input (e.g.,
  NUR for Nix-packaged Firefox extensions) introduced just to unify the two mechanisms.
- **VI. Secure by Default** — PASS. No firewall, authentication, or network-exposure
  change. Force-installing specific, developer-chosen extensions via enterprise policy
  is the standard, intended mechanism for managed browser deployments and doesn't weaken
  the host's security posture; if anything, a content blocker improves the everyday
  browsing security/privacy posture.
- **Secrets Management** — N/A. No secret is introduced or stored in the repository;
  each extension's own login/session state (notably Bitwarden's) is created by the
  developer at first use.

No violations. Complexity Tracking is not needed.

### Source Code (repository root)

```text
modules/nixos/
├── browser-extensions.nix  # NEW — programs.chromium + programs.firefox.policies config
├── desktop-apps.nix         # existing — Chrome/Obsidian/Bitwarden/GitKraken (unchanged)
└── users.nix                 # existing — programs.firefox.enable stays as-is (unchanged)

hosts/laptop/
└── configuration.nix         # add one import line for modules/nixos/browser-extensions.nix
```

**Structure Decision**: Single NixOS flake configuration repo. One new shared module,
`modules/nixos/browser-extensions.nix`, holds both browsers' extension policy — Chrome
and Firefox are kept in the same file (rather than split further) because the four
extension *families* are the natural unit of reasoning here, and each family needs a
paired Chrome ID + Firefox policy entry side by side for the file to stay legible;
splitting by browser would scatter each family's two halves across two files for no
benefit at this scale (Constitution Principle V). The module is imported from
`hosts/laptop/configuration.nix`, alongside the existing `desktop-apps.nix` import.
